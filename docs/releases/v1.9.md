This release moves the verifier to the Dockerfile frontend 1.29 (BuildKit v0.35.0, #553). It retires dockerfile 1.27 from the verifier's allowlist, refuses the new `--unset` and `--reset` flags explicitly on every instruction, and drops the heredoc restriction that applied only to 1.27. The images it accompanies are built with the 1.29 frontend and ship gh 2.105.0.

**Tag:** `v1.9`, on the commit this Release page shows. Pin the reusable workflows to that commit's full SHA, never to the tag name: each called workflow checks that it was pinned by SHA. The tag is created by the release workflow's App and is not GPG-signed. The consumer lint (`tools/check-consumer-workflows.sh`) and this repo's `tools/check-self-pins.sh` check that a pin's `# vX.Y` comment names a tag that peels to the pinned commit.

## Upgrade

The template files at this tag still pin `v1.8`, and the template's `.devcontainer/Dockerfile` line 1 is still dockerfile 1.28, because a commit cannot pin its own release. Use the tag's commit SHA, or copy the template from the pin-bump PR that follows this release.

### First: a repo still on dockerfile 1.27 moves line 1

From `v1.9` the verifier allows only dockerfile 1.29 (`CurrentSyntax`) and 1.28 (`PreviousSyntax`) on line 1 of `.devcontainer/Dockerfile`. A repo whose line 1 is still `# syntax=docker/dockerfile:1.27@sha256:4edf897a…` fails `verify / verify` once its verify pin moves to `v1.9`. How it moves depends on the pin it is on now:

- **Pinned to `v1.5` through `v1.8`** (their verifiers allow 1.28 and 1.27): move line 1 to 1.28 first, in its own PR under the current pin, then re-pin to `v1.9`. The 1.28 line is `# syntax=docker/dockerfile:1.28@sha256:bb22d9815c728170f72750f4e5b0d672e06176142e1d602c7e66c050100b7e5b`.
- **Pinned to `v1.4` or earlier** (its verifier allows 1.27 only): move line 1 in the same PR that re-pins to `v1.9`. A 1.28 or 1.29 line fails the older verifier, so the two cannot be split.

A legacy-gate repo that re-pins before moving line 1 also loses auto-merge: a `v1.9` `decide` refuses the repo's head Dockerfile, so every image bump goes to review, and `verify / verify` is red too.

Moving line 1 to 1.29 is optional, and only with or after the re-pin to `v1.9`: the `v1.8` verifier allows 1.28 and 1.27 only. The 1.29 line is `# syntax=docker/dockerfile:1.29@sha256:572cebbc2b15e6f84c077742952674889cb63cd5e9b80abdffcbe587b6f19183`.

### Every consuming repo

1. **Re-point the pins** to `@<full SHA of the v1.9 tag's commit> # v1.9`. Dependabot's `github-actions` ecosystem proposes this as a reviewed PR.
   - `devcontainer-image.yml`: the verifier. Its Dockerfile rules changed (below).
   - `secret-scan.yml`: unchanged since `v1.8`. The scanner stays betterleaks 2.0.0-rc.8.
   - Legacy-gate repos only: `devcontainer-bump-decision.yml` in the gate's `decide` job. Keep it on the same SHA as the verify pin, or the consumer lint warns. The gate itself is unchanged apart from that pin, so it does not need re-copying.
2. **Re-run the consumer lint** from a checkout of this repo at `v1.9`: `<checkout>/tools/check-consumer-workflows.sh <your-repo>/.github/workflows`. Its rules are unchanged since `v1.8`.

A repo pinned to a release older than `v1.8` also takes the upgrade steps in the notes of each release it skips: for example `v1.8`'s move of the secret scan to betterleaks 2.0.0-rc.8, whose default rules changed, and, for a dev-App repo still on the `v1.6` template, `v1.7`'s template change, which a `v1.9` verifier requires.

### Dev-App repos: the template window

The `v1.9` verifier accepts the `v1.9` dev-App template and a snapshot of the `v1.8` template. Both are identical to the `v1.7` template: `template/.devcontainer/` has not changed since `v1.7`. A repo on any of those templates moves its verify pin to `v1.9` with no template change, after the line 1 step above if it is still on 1.27.

## Behaviour changes in `verify / verify`

- **dockerfile 1.27 is no longer allowed** on line 1, as above.
- **Heredocs are allowed on both allowed syntaxes.** The rule that a Dockerfile on the previous syntax may not contain `<<` existed only because the 1.27 frontend's shell lexer read heredocs differently from the verifier's. It goes with 1.27: 1.28 and 1.29 lex them the same. A 1.28 file with a heredoc was already accepted, so this changes no file's result on its own.
- **An `--unset` or `--reset` flag is refused on any instruction**, in any letter case and with any value (`--unset=false` included), under both syntaxes. BuildKit v0.35.0 adds `ENV`, `LABEL` and `VOLUME --unset` and `FROM --reset`, which could strip the labels, environment or user the base image sets. They sit behind the `dfunset` and `dfreset` build tags, which the mainline 1.29 frontend does not set, but the verifier refuses the flags outright rather than rely on that. The `v1.8` verifier already refused them as unknown flags everywhere except on `ARG` and `STOPSIGNAL` (next bullet); the explicit rule keeps them refused if a frontend ever registers them.
- **A flag on `ARG` or `STOPSIGNAL` is refused.** The 1.28 frontend ignored a flag there; the verifier's BuildKit now parses flags on both and knows none, so a Dockerfile carrying one (for example `ARG --foo V=1`) fails as instructions that do not parse. This only refuses files that were accepted before; no Dockerfile that passes is read differently.

No other verifier, `decide`, reusable-workflow or consumer-lint behaviour changed.

## Image changes

The images publish on every push to `main` and reach consumers by digest through Dependabot, independently of this tag. These landed between `v1.8` and `v1.9`:

- **Built with the dockerfile 1.29 frontend** (#553): line 1 of each image's Dockerfile moved from 1.28. Nothing in the images uses the new 1.29 forms.
- **gh 2.105.0** (from 2.104.0, #602), which also retired gh's Trivy exception for CVE-2026-78661.
- **The remaining Trivy exceptions were renewed to 2026-12-17** (#484), after a fresh no-ignore re-scan. Each still covers one binary's path, with its reason in `.trivyignore.yaml`.

## Known gaps (still open)

- **The image scan does not see the interpreter** (DEVC-D11). Trivy identifies no component under `/opt/devc/python`, and the image's SBOM does not list it.
- **The consumer lint misses one mistake** (#521). It does not warn when a dev-App repo pins a verifier older than dev-App mode. Today the error appears only as a `verify / verify` failure.
