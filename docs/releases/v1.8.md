This release moves the org secret scan to betterleaks 2.0.0-rc.8. The images it accompanies make a pinned CPython 3.15 the default `python3`. It is also the first release whose verifier window no longer includes the `v1.6` dev-App template: a dev-App repo still on that template takes the `v1.7` template before it moves its verify pin.

**Tag:** `v1.8` → `<SHA>`. Pin the reusable workflows to that SHA, never to the tag name: each called workflow checks that it was pinned by SHA.

## Upgrade

The template files at this tag still pin `v1.7`, because a commit cannot pin its own release. Use the SHA above, or copy the template from the pin-bump PR that follows this release.

### Every consuming repo

1. **Re-point the pins** to `@<SHA> # v1.8`. Dependabot's `github-actions` ecosystem proposes this as a reviewed PR.
   - `secret-scan.yml`: this moves the repo's CI scan from betterleaks 2.0.0-rc.7 to rc.8, because the workflow reads `BETTERLEAKS_VERSION` from the Dockerfile at the pinned commit. The default rules changed in between. rc.8 drops the stopword list from `generic-api-key`, treats `)` as a token boundary, adds a Cypress credentials rule, and filters some known false positives. The first scan on the new pin can therefore report findings rc.7 did not, mostly from `generic-api-key`. Fingerprints hash the secret value, so existing ignore-file entries still match. Review any new finding the first scan reports like any other. This pin is independent of the others.
   - `devcontainer-image.yml`: the verifier. Its code is unchanged since `v1.7`, but its accepted templates moved (below).
   - Legacy-gate repos only: `devcontainer-bump-decision.yml` in the gate's `decide` job. Keep it on the same SHA as the verify pin, or the consumer lint warns. The gate itself is unchanged apart from that pin, so it does not need re-copying.
2. **Re-run the consumer lint** from a checkout of this repo at `v1.8`: `<checkout>/tools/check-consumer-workflows.sh <your-repo>/.github/workflows`. Its rules are unchanged since `v1.7`.

### Dev-App repos: the template window moves

Each release's verifier accepts its own dev-App template and the one before it. The `v1.8` verifier accepts the `v1.8` template and a snapshot of the `v1.7` template, and those two are identical: `template/.devcontainer/` did not change between the tags. The `v1.6` template is no longer accepted.

- **A repo on the `v1.7` template** moves its verify pin to `v1.8` with no other change.
- **A repo still on the `v1.6` template** takes the `v1.7` template change first. That change is the plugin install at the end of `postStartCommand` (#503), which needs an image from after `4158d91`. The `v1.7` notes give its steps. Move the verify pin to `v1.8` in that PR or after it. A `v1.8` verifier rejects the `v1.6` template, so `verify / verify` fails if the pin moves first.

### Python 3.15 in the images (#556)

The images publish on every push to `main` and reach consumers by digest through Dependabot, independently of this tag. From the base-image build of `146ed30` (#557) on, `python3`, `python` and `python3.15` are a pinned CPython 3.15.2 from python-build-standalone release 20261110, installed under `/opt/devc/python`. `/usr/bin/python3` stays Ubuntu's 3.14, for apt's own tools and the image's tools venv. (DEVC-D11 records the decision.)

When a repo takes that image digest:

- **Recreate the repo's `.venv`.** The `/workspace/.venv` volume keeps the interpreter it was made with, and an existing one was made with Ubuntu's 3.14. `python3 -m venv` now makes a 3.15 venv with its own pip.
- **Check that the dependencies install on 3.15.** A package with no CPython 3.15 wheel needs a source build. PyYAML 6.0.3 is one such package today, which is why the image's own tools venv stays on 3.14.
- **Move the repo's CI to 3.15.** DEVC-D11 cites consuming repos running `actions/setup-python` at the image's version. Until a repo moves that pin, its container and its CI differ on Python's minor version. Each repo's move is tracked on #556.
- **Expect pip only inside a venv.** The interpreter has no pip module and carries a PEP 668 `EXTERNALLY-MANAGED` marker, so `python3 -m pip install` outside a venv is refused.

## Image changes

These landed between `v1.7` and `v1.8`:

- **The default interpreter is CPython 3.15.2** (#557), as above. The smoke test checks it on every build: the pinned version, both interpreters, the symlinks and their ownership, the missing pip module, the PEP 668 marker, the TLS CA store, and uv's lookup of 3.15. It also checks that `python3 -m venv` seeds a pip that runs (#563).
- **The interpreter is re-pinned weekly within its minor** (#564). `bump-binaries.yml` now opens a `bump/python-<version>-<build>` PR when python-build-standalone publishes a newer build of 3.15. A move to another minor stays a deliberate hand re-pin.
- **Tool bumps:** betterleaks 2.0.0-rc.8 (from rc.7, #541), gh 2.104.0 (#542), uv 0.13.8 (#539), Node 26.13.1 (#540).

## Known gaps (still open)

- **The image scan does not see the interpreter** (DEVC-D11). Trivy identifies no component under `/opt/devc/python`: not CPython, not the OpenSSL it links, not its bundled ensurepip wheels. The image's SBOM does not list it either. The weekly re-pin is prompted by a newer build, not by a scan finding.
- **The consumer lint misses one mistake** (#521). It does not warn when a dev-App repo pins a verifier older than dev-App mode. Today the error appears only as a `verify / verify` failure.
