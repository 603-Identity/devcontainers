This release adds the dev-App route (DEVC-D9, #418). A dev-App repo's container gets a per-repository GitHub App token instead of a PAT, and no signing agent. It ships two new images, `devcontainer-devapp` and `devcontainer-devapp-tofu`, and a verifier mode that holds a dev-App repo to the template. `template/.devcontainer/` is now dev-App only. The legacy PAT route is frozen: existing legacy repos keep working, but the verifier's plain mode is now an allowlist, so check them against it before re-pinning.

These notes were written on 2026-11-10, after `v1.7`: `v1.6` shipped as a tag only (#486). Known gaps are as of that date.

**Tag:** `v1.6` → `58d54dd63228e3640327bfcd34d91f64fcc88e60` (signed). Pin the reusable workflows to that SHA, never to the tag name: each called workflow checks that it was pinned by SHA.

## Upgrade

The template files at this tag still pin `v1.5`, and the `v1.5` verifier rejects a devapp `FROM`. Do not adopt from `template/` at this tag. Use the SHA above, or copy the template from `9cbbe84` (#468), which pins `v1.6`.

### Legacy-route repos (the PAT route)

1. **Do not copy `template/.devcontainer/`.** It is the dev-App template now. The legacy procedure stays in the README at [`9af5b4c`](https://github.com/603-Identity/devcontainers/blob/9af5b4c/README.md#using-an-image-in-a-repo).
2. **Check both `.devcontainer/` files against the new rules before re-pinning.** Each of these passed under `v1.5` and fails `verify / verify` under `v1.6`:
   - in `devcontainer.json`, anything outside plain mode's allowlist (below): for example a host bind mount, an object-form mount, an `appPort`, a `${localEnv:...}` substitution, or a changed `runArgs`, `workspaceFolder` or `workspaceMount`;
   - in the `Dockerfile`, a `LABEL devcontainer.metadata`, or a `<<` (heredoc) while the `# syntax=` line is still dockerfile 1.27;
   - in either file, a dev-App marker (`devcontainer-devapp`, `glunk-identity` or `/run/wow`), comments included.
3. **Re-point all three pins** to `@58d54dd63228e3640327bfcd34d91f64fcc88e60 # v1.6`:
   - `devcontainer-bump-decision.yml`, in the gate's `decide` job. Keep it on the same SHA as the verify pin, or the consumer lint warns.
   - `verify-devcontainer-image.yml`, in `devcontainer-image.yml`.
   - `secret-scan.yml`, in `secret-scan.yml`. The secret scan itself is unchanged since `v1.4`.

   The gate's logic is unchanged since `v1.4`: only its header comment and the pin moved. It does not need re-copying.
4. **Re-run the consumer lint** from a checkout of this repo at `v1.6`: `<checkout>/tools/check-consumer-workflows.sh <your-repo>/.github/workflows`. A legacy repo gets the same rules as under `v1.5`.

### New dev-App repos

Follow [`docs/adopting.md` at `9cbbe84`](https://github.com/603-Identity/devcontainers/blob/9cbbe84/docs/adopting.md), which is written for the dev-App route. A legacy repo moving to dev-App follows the same runbook. Its step 6, "Cutting over from the legacy layout", has the cleanup that move needs. In outline:

- **Secret scanning moves first,** as its own PRs (runbook step 1).
- **Then the approval ruleset,** before the dev App is installed: at least 1 approving review, code-owner review, a `CODEOWNERS` file and no bypass actors. `verify / verify` reads the first two and fails without them.
- **Copy `template/.devcontainer/`** and change only `OWNER/REPO` in the token mount and the `FROM`, which must be `devcontainer-devapp` or `devcontainer-devapp-tofu` by tag and digest. Repo-specific tools go between the `FROM` and the final `USER 1000:1000`. An optional loopback-only `appPort` is the one other change allowed.
- **Copy only two workflow callers,** `devcontainer-image.yml` and `secret-scan.yml`. **Do not copy `architect-review-gate.yml`**: a dev-App repo's review gate is the way-of-working plugin's `review.ci_gate`, which posts the same `architect-review` check.
- **Windows hosts only.** The host broker writes the token under `%USERPROFILE%\.config\glunk-identity\tokens\<owner>\<repo>\`. VS Code attach is unsupported in a dev-App container. The README's "Using an image in a repo" gives the interim devcontainer CLI entry and the precautions it needs.

## Behaviour changes

- **The verifier reads the repo's mode** (#451). A repo is dev-App when the PR head, the PR base or the default branch's tip is. The base and tip are read leniently, as raw bytes, so a broken base never blocks its own repair. An API error is red. A plain repo's `Dockerfile` and `devcontainer.json` must not name a dev-App marker (`devcontainer-devapp`, `glunk-identity` or `/run/wow`), comments included.
- **Plain mode is an allowlist.** `runArgs`, `workspaceFolder` and `workspaceMount` must be exactly the legacy template's. Each mount must be a legacy mount or a per-repo `${localWorkspaceFolderBasename}-<name>` volume. `${localEnv:`, `${env:` and `${localWorkspaceFolder}` may appear only in those exact strings. `appPort`, `privileged`, `capAdd`, `securityOpt`, `initializeCommand` and object-form mounts are refused. So no host bind can be added.
- **Dev-App mode compares `devcontainer.json` with the template** at the pinned release, as parsed JSON, outside four per-repo surfaces: the token mount's `tokens/<owner>/<repo>`, which must equal the repository's name in GitHub's case; an optional loopback-only `appPort`; the `FROM`, a devapp image no older than the base's; and the Dockerfile extras. The extras filter catches accidents, not attacks: no `ENV` of `GIT_*`, `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` (#465) or `ANTHROPIC_BASE_URL`, nothing that names or writes the identity layer's paths, and no local `ADD`.
- **Dev-App mode reads the default branch's rules.** It fails unless a `pull_request` rule requires at least 1 approval and code-owner review.
- **`decide` exits 3 for a dev-App image,** so a dev-App image bump is never armed for auto-merge. A human approves and merges it.
- **Both modes refuse `LABEL devcontainer.metadata`** in the Dockerfile.
- **A Dockerfile still on dockerfile 1.27 may not contain `<<`** (a heredoc), in a line or across a line continuation (#429). The vendored 1.28 lexer, the one file that changed between the two frontends, is reached by heredoc parsing. Move the `# syntax=` line to 1.28 first.

## Consumer lint (`tools/check-consumer-workflows.sh`)

- **A dev-App profile** (#451). The lint detects a dev-App repo from its `.devcontainer/` files, by the same markers the verifier reads. In a dev-App repo:
  - the template gate's jobs (`resolve`, `decide`, `post`, or a call to the decide workflow) are findings;
  - the gate rules are skipped;
  - one job is exempt from the write rule: the plugin gate's status writer, held to the template `post` job's shape.
- A legacy repo's rules are unchanged.

## This repo only (no action for consumers)

- **`tools/check-self-pins.sh`** (#430, closes #125) checks in CI that the five self-pins (the template's callers and gate, `tools/gate-template.yml.in`, and this repo's own gate) agree, are on `main` with a tag that peels to them, and that the pinned release's verifier allows the template's `# syntax=` line. A newer tag than the one pinned only warns.
- A `# syntax=` bump is now two steps: the image Dockerfiles and the verifier first, then a release, then the template's line with the pin bump (#435).

## Images

Images publish on merges to `main` that change an image, and on the weekly schedule, not on tags. Take them through Dependabot's digest bumps as usual. Since `v1.5`:

- **New: `devcontainer-devapp` and `devcontainer-devapp-tofu`** (#442), built from the base and tofu images of the same run. They add the identity layer: `dev-token` as git's only credential helper, reading `/run/wow/dev-token` and failing closed without it; a `gh` wrapper; ssh remotes rewritten to https; no gpg and no commit signing. They ship Claude Code 2.1.316, verified against Anthropic's signed manifest, with updates disabled.
- **Tool bumps:** gh 2.103.3.
